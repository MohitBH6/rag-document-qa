# 📚 RAG Document Q&A

A Retrieval-Augmented Generation (RAG) system that lets you upload PDF documents and ask questions about them in plain English. Answers are grounded in the actual document content and backed by source citations, so you always know where an answer came from.

Built to understand and demonstrate the core RAG pipeline used in modern AI-native applications: document chunking, embedding generation, vector storage, semantic retrieval, and LLM-based answer generation.

---

## ✨ Features

- 📄 Upload one or more PDF documents directly in the browser
- 🔍 Semantic search over document content — not just keyword matching
- 🤖 Answers generated by an LLM, grounded strictly in retrieved context
- 📌 Every answer comes with the exact source chunks it was based on
- ⚡ Fast inference via Groq's cloud API
- 🖥️ Two interfaces: a Streamlit web UI and a command-line tool

---

## How It Works

1. **Upload** — PDFs are uploaded through the browser UI (or placed in a folder for CLI use)
2. **Chunk** — Documents are split into overlapping text chunks (~1000 characters, 200-character overlap) so related ideas aren't cut apart at chunk boundaries
3. **Embed** — Each chunk is converted into a vector embedding — a list of numbers that captures its meaning — using a local embedding model
4. **Store** — Embeddings are saved in ChromaDB, a vector database optimized for similarity search
5. **Retrieve** — When you ask a question, it's embedded the same way and compared against every stored chunk to find the most relevant ones
6. **Generate** — The retrieved chunks are passed to an LLM as context, which generates an answer grounded in that content
7. **Cite** — The answer is returned alongside the specific source chunks and page numbers it was built from

## Tech Stack

| Component | Technology |
|---|---|
| Orchestration | LangChain (LCEL chains) |
| LLM | Groq API — `openai/gpt-oss-20b` |
| Embeddings | HuggingFace `sentence-transformers` — `all-MiniLM-L6-v2` (runs locally) |
| Vector Store | ChromaDB |
| Web UI | Streamlit |
| Document Processing | `RecursiveCharacterTextSplitter`, `PyPDFLoader` |

## Setup

### 1. Clone and enter the project

```bash
git clone <this-repo-url>
cd langchain-rag-project
```

### 2. Create a virtual environment

```bash
python -m venv venv
venv\Scripts\activate      # Windows
source venv/bin/activate   # macOS/Linux
```

### 3. Install dependencies

```bash
pip install -r requirements.txt
pip install streamlit langchain-huggingface langchain-groq sentence-transformers
```

### 4. Configure environment variables

Copy `.env.example` to `.env` and add your Groq API key (free at [console.groq.com](https://console.groq.com)):

```env
GROQ_API_KEY=your_key_here
GROQ_MODEL=openai/gpt-oss-20b
EMBEDDING_MODEL=all-MiniLM-L6-v2
CHROMA_PERSIST_DIRECTORY=./data/chroma_db
CHUNK_SIZE=1000
CHUNK_OVERLAP=200
RETRIEVAL_K=4
```

## Usage

### Option A: Web UI (recommended)

```bash
streamlit run streamlit_app.py
```

Opens a browser at `http://localhost:8501`. Upload PDFs in the sidebar, click **"Process Documents,"** then ask questions in the main panel.

### Option B: Command line

```bash
# Index documents
python main.py --load data/papers/

# Ask a question with streaming output
python main.py --query "your question here" --stream
```

## Design Notes

- **Chunk size (1000 chars) with overlap (200 chars):** balances retrieval granularity against losing context at chunk boundaries. Overlap ensures sentences spanning a boundary aren't lost entirely from either chunk.
- **Local embeddings:** using `sentence-transformers` instead of a cloud embedding API keeps the system free to run and avoids sending document content to a third party for the embedding step.
- **Groq for generation:** chosen for its free tier and low-latency inference, which was useful for fast iteration during development.
- **Explicit source citation:** every answer includes the retrieved chunks it was generated from, making the system's reasoning auditable rather than a black box.

---

## Known Limitations

- Retrieval uses plain similarity search (top-k) without re-ranking — could surface less relevant chunks in a large or diverse document set
- No conversation memory — each question is answered independently, without context from prior questions
- PDF-only input; no support for other document formats yet
- Single embedding model; no comparison against alternatives for retrieval quality

## Possible Improvements

- Add a re-ranking step (e.g. cross-encoder) to improve retrieval precision
- Support multi-turn conversations with memory
- Add support for `.docx`, `.txt`, and web page inputs
- Experiment with different chunk sizes/overlap and measure retrieval quality empirically
